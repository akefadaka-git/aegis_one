# AEGIS ONE — Device Identity and Recovery Contract

**ID:** AEGIS-CONTRACT-G01-001 | **Version:** 1.0 | **Status:** A2 proposed contract; approval required

## 1. Purpose
Define how an AEGIS installation becomes a registered device instance, how it proves continuity, and how loss, replacement, compromise, or revocation is handled. A hardware identifier is not a person or account identity.

## 2. Identity objects
- **Account principal:** authenticated user or organization identity established by the identity provider.
- **Installation identity:** random, installation-scoped identifier generated by AEGIS; not an IMEI, MAC address, serial number, or advertising identifier.
- **Device record:** server-side association of account/tenant, installation identity, device profile, status, and key metadata.
- **Device key:** asymmetric key pair generated locally. Private key is non-exportable where supported and used only for defined cryptographic purposes.
- **Attestation evidence:** optional evidence about key origin/device state, separately validated by a backend verifier. It is not the identity itself.
- **Management enrollment:** separate Android Enterprise state, present only where provisioning establishes the relevant management role.

## 3. Registration protocol
1. Authenticate the account principal.
2. Generate a cryptographically secure random installation ID and device key pair locally.
3. Obtain a server challenge with unique nonce, short expiry, and registration scope.
4. Bind the public key to the challenge and registration request.
5. Where supported and required, collect Android Key Attestation and submit the full chain and challenge to a backend verifier.
6. Backend validates challenge freshness, certificate chain against current trusted roots, revocation status, attestation security level, verified boot/device-lock claims, app identity claims, and policy version.
7. Register as PENDING_VERIFICATION until required checks pass; then ACTIVE or a documented restricted state.
8. Issue a scoped device credential with audience, key ID, expiry, and revocation reference.

Client-side interpretation alone is insufficient for remote trust decisions. Missing or unsupported attestation is UNKNOWN, not PASS.

## 4. Lifecycle states
UNREGISTERED → PENDING_VERIFICATION → ACTIVE → RESTRICTED → REVOKED.
Additional states: LOST, REPLACED, RECOVERY_PENDING, DECOMMISSIONED.

Every transition requires an authenticated actor, allowed transition, reason, timestamp with clock-quality metadata, and audit event. Revocation is monotonic: a revoked installation key is never reactivated; a new installation registers with a new key and identity.

## 5. Lost-device and recovery
- User can mark a device lost from an authenticated recovery channel.
- Lost state blocks new remote commands except explicitly defined recovery actions.
- Remote lock/wipe are not automatic; each requires a separately approved command class, high-assurance authorization, impact confirmation, and audit evidence.
- Recovery verifies account ownership using an independent recovery method; possession of the lost device alone is insufficient.
- Reinstallation creates a new installation identity and key. It does not inherit old grants.
- Device replacement does not transfer private keys from the old device.
- Emergency contacts are notification/recovery contacts, not automatic administrators.

## 6. Privacy
Do not collect IMEI, phone number, contacts, location, or other identifiers unless a separately documented requirement, permission, purpose, retention, and consent/legal basis are approved. Device identifiers must not be used for cross-app tracking.

## 7. Required negative tests
Challenge reuse/expiry/malformed scope; invalid or revoked attestation chain; unknown trust root; key mismatch; duplicate registration; cross-account binding; revoked-key reuse; reinstall/restore attempting to resurrect grants; lost-device non-recovery commands; clock rollback.

## 8. Open decisions
Identity provider and authentication factors; backend attestation verifier and trust-root owner; family vs enterprise registration approval; recovery factor policy; blocking vs restricted-mode attestation failure.

No implementation is authorized by this contract.
